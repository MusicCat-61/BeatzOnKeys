## English

1.3.2 fixes a bug where a second search left the first one's caching running behind it.

### What went wrong

- **Every search started a background pass that fetched all of its results**, so the rows could be listened to and kept without another wait. Nothing ever stopped the previous pass.
- **A second search therefore ran two passes at once.** The old one kept downloading rows the user no longer saw, and both competed for the same two download slots — so the new rows queued behind work that was already pointless.
- **The cache figures stopped moving**, because they were only refreshed at the end of a whole pass, which now came much later.
- **The «Добавить» button stayed dead** even after the file had arrived: the button follows a command, and a command re-checks only when it is told to. Nothing told it.

### What changed

- **A new search cancels the previous pass** through its own token, linked to the view model's lifetime so closing the window still stops it. The rows of the cancelled pass are already gone from the list, so nothing is lost.
- **The button is told to re-check the moment a file lands**, and the cache figures are refreshed after every row rather than once at the end.

### A note on the tests

- **The first version of the regression check passed against the broken code**, because it asked the command directly — and a command answers correctly even when nobody has asked it to re-check. It now counts the change notifications instead, which is the only thing that distinguishes a working binding from a dead one, and it fails on the old code as it should.

## Русский

1.3.2 исправляет баг: второй поиск оставлял позади себя кеширование первого.

### Что ломалось

- **Каждый поиск запускал фоновый проход, скачивающий все его результаты**, чтобы строки можно было слушать и добавлять без ожидания. Останавливать предыдущий проход было некому.
- **Второй поиск запускал два прохода одновременно.** Старый продолжал качать строки, которых пользователь уже не видит, и оба дрались за одни и те же два слота загрузки — новые строки вставали в очередь за работой, которая уже была бессмысленной.
- **Цифры кеша переставали меняться**, потому что обновлялись только в конце целого прохода, а он теперь наступал заметно позже.
- **Кнопка «Добавить» оставалась мёртвой** даже после появления файла: кнопка следует за командой, а команда перепроверяет себя только когда её об этом попросят. Просить было некому.

### Что изменилось

- **Новый поиск отменяет предыдущий проход** через собственный токен, связанный с временем жизни модели представления, так что закрытие окна его всё равно останавливает. Строки отменённого прохода уже убраны из списка, так что терять нечего.
- **Команде приказывают перепровериться в момент появления файла**, а цифры кеша обновляются после каждой строки, а не один раз в конце.

### Замечание про тесты

- **Первая версия регрессионной проверки проходила на сломанном коде**: она спрашивала команду напрямую, а команда отвечает правильно даже тогда, когда её никто не просил перепровериться. Теперь проверка считает уведомления об изменении — единственное, что отличает работающую привязку от мёртвой, — и на старом коде краснеет, как и должна.
