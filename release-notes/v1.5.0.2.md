## English

1.5.0.2 fixes a lock that could pump the message queue, found by the CI runner rather than by me.

### The keyboard hook no longer pumps the caller's message queue

- **It used `lock`, and a contended `lock` calls `SynchronizationContext.Wait`.** On a thread that has a dispatcher — the WPF UI thread, for instance — that wait pumps the message queue while the hook is still half installed, so unrelated dispatcher work can run against an unfinished installation. The class has a test forbidding exactly that, and the test passed here for a year because the gate is never contended on a quiet desktop. The CI runner is busier, took the slow path, and failed.
- **The gate is a spin lock built on `Interlocked` alone now**, so it never consults a synchronization context. The critical sections are a handful of field assignments, so a short spin costs less than any wait.
- **`Monitor.TryEnter` was not enough**, and this is worth saying plainly: the first attempt used it, and the contention test failed with the same stack, because `TryEnter` also ends up in `Monitor.Enter_Slowpath`. The fix was measured, not assumed.
- **Re-entry is reported instead of hanging.** No current caller nests, which the suite exercises end to end, so the throw is a tripwire rather than a path.

### A test that forces what the old one only hoped for

- **`KeyboardHook.ContendedGateNeverPumpsTheCallerContext` holds the gate from another thread**, so contention is guaranteed rather than dependent on how busy the machine is, and then installs from a thread whose synchronization context rejects waits.
- **The test was proved non-vacuous both ways**: with a blocking gate it fails with the same "pumping managed wait" stack, and it hangs the suite outright, which is the failure mode the design is buying its way out of.

## Русский

1.5.0.2 исправляет блокировку, которая могла прокачивать очередь сообщений. Нашёл её CI-раннер, а не я.

### Хук клавиатуры больше не прокачивает очередь сообщений вызывающего

- **Он использовал `lock`, а `lock` при конкуренции вызывает `SynchronizationContext.Wait`.** На потоке с диспетчером — например, на UI-потоке WPF — это ожидание прокачивает очередь сообщений, пока хук ещё не доустановлен, и посторонняя работа диспетчера может выполниться посреди установки. В классе есть тест, который это прямо запрещает, и он проходил у меня год, потому что на спокойном рабочем столе конкуренции нет. Раннер занят сильнее, ушёл в медленный путь — и упал.
- **Теперь это спин-блокировка только на `Interlocked`**, поэтому синхронизационный контекст не опрашивается вообще. Критические секции здесь — несколько присваиваний полей, так что короткий спин дешевле любого ожидания.
- **`Monitor.TryEnter` не подошёл**, и это стоит сказать прямо: первая попытка была с ним, и тест на конкуренцию упал с тем же стеком, потому что `TryEnter` тоже уходит в `Monitor.Enter_Slowpath`. Исправление измерено, а не предположено.
- **Повторный вход теперь сообщается, а не вешает.** Сегодня ни один вызов не вкладывается — набор тестов проходит это насквозь, — поэтому исключение работает как растяжка, а не как рабочий путь.

### Тест, который создаёт то, на что старый только надеялся

- **`KeyboardHook.ContendedGateNeverPumpsTheCallerContext` держит ворота с другого потока**, поэтому конкуренция гарантирована, а не зависит от занятости машины, и ставит хук с потока, чей синхронизационный контекст запрещает ожидания.
- **Тест проверен в обе стороны**: с блокирующими воротами он падает с тем же стеком «pumping managed wait» и вешает весь прогон — ровно тот отказ, от которого уходит эта конструкция.
